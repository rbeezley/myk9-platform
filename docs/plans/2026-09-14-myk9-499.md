# MYK9-499 — checkout confirmation matches My Shows

The September 2026 registration-wizard redesign is complete. MYK9-497 and
MYK9-498 have since merged; this plan covers the still-open confirmation issue.
This is a narrow bug repair, so no new OpenSpec surface is needed.

## Implementation

1. Reconcile refunds first when an order is inserted as `succeeded`, then run
   the existing enrollment logic through an update if the order remains paid.
   Retain update idempotency. The order and its entries must link to the same
   enrollment/`MK9-` number. Backfill eligible historical cart orders.
2. Return the enrollment number as the exhibitor-facing confirmation. A Stripe
   PaymentIntent ID remains a support reference, never a `Confirmation #`.
3. Keep the existing My Shows enrollment read; do not create a second receipt
   surface or bypass the owner-scoped checkout lookup.

## Testing and evidence

1. Write an assertion-first regression for the exact `pi_` value being returned
   as a confirmation and run it red before changing the implementation.
2. Add a transactional SQL test proving successful INSERT, later UPDATE, and
   repeated success share one enrollment and link the paid entry. Include a
   refund that arrived before the order. The SQL test is registered for CI;
   local execution requires a database runtime.
3. Run focused checkout tests, app typecheck, targeted lint, migration guard,
   code-quality ratchet, and diff checks. Review with two Codex subagents as
   the user-requested fallback; do not invoke Claude.

Deployment of the migration is a separate shared-system gate after merge.
