## Uncoordinated sync loops — 2026-05-25 10:16

- **Unify the two uncoordinated `isSyncing` loops in myK9Q** - The offline queue and the sync-status surface each maintain their own `isSyncing` flag in separate Zustand stores, and there is no single owner deciding "a sync is in flight right now." **Problem:** `useOfflineQueueProcessor` guards work with `processingRef.current || isSyncing` while `offlineQueueStore.startSync` independently flips its own `isSyncing` field, and `addToQueue` fires a `setTimeout(() => get().startSync(), 100)` without informing the processor. If the queue's `startSync` path crashes between `isSyncing: true` (set at `offlineQueueStore.ts:176`) and the `finally`-equivalent reset (`offlineQueueStore.ts:206`), the flag stays `true` and blocks subsequent runs of either loop. This is what made the processor test initially fragile — racing the two loops produced flake. It is also an ambient risk in production: a one-time crash can wedge sync until app reload. **Files:** `apps/myk9q/src/stores/offlineQueueStore.ts:53,64,84,132-133,164,168-176,206,227,307` (queue's own `isSyncing` + `startSync` + the auto-fired `setTimeout`), `apps/myk9q/src/stores/syncStatusStore.ts:23,50,62,111-112` (parallel `isSyncing` on the sync-status surface), `apps/myk9q/src/hooks/useOfflineQueueProcessor.ts:22,108,122,130` (processor reading the status-store flag + its own `processingRef`). **Solution:** Collapse to a single owner. Two reasonable shapes — (a) make `offlineQueueStore` the source of truth and have `syncStatusStore.isSyncing` become a selector derived from it (drop the duplicate field); (b) hoist sync orchestration to a single hook/manager that owns both flags and the queue's processing semaphore, and have `addToQueue` request work via that manager instead of `setTimeout(startSync, 100)`. Either way, add a `try/finally` (or equivalent) around every place that sets `isSyncing: true` so a thrown error cannot leave the flag latched. Add a regression test asserting that a `startSync` that throws still clears `isSyncing` and that a second `addToQueue` can drive a new sync. Related: this is the architectural cleanup hinted at in the "Move placement server-side, drop `submitScore`" follow-up — both items want one canonical sync path.
  - **Resolved 2026-05-25:** `useOfflineQueueProcessor` is now the only score-queue worker. Removed `offlineQueueStore.isSyncing`, `startSync`, and `syncComplete`; score-sync UI derives active syncing from `queue` item statuses. Removed `syncManager.processOfflineQueue` so `syncManager` no longer double-submits queued scores on manual sync or online transitions. Regression tests cover add-to-queue, offline→online, hydration, and processor retry behavior.

## Dog photo upload does not persist — 2026-06-03 14:18

- **Fix dog photo upload not persisting** - On the dog detail page (`https://myk9show.com/dogs/:id`, e.g. `85ac647d-2b30-4143-9323-830395b65fb4`) adding/changing a photo showed a "Photo updated successfully" toast and a celebration, but navigating away and back showed the old/placeholder photo — the change was never saved. **Problem:** The photo save handler only mutated local component state; it never called the DB update mutation, and the picked image was never uploaded to Storage. In `DogDetailsMain/index.tsx`, `handlePhotoSave(preview)` did `if (preview) setUpdatedDog({ ...updatedDog, imageUrl: preview })` and closed the dialog — that was it (no `onUpdate` / persistence). The success toast + celebration in `DogDialogs.tsx` fired unconditionally after the local-state set, so the UI falsely reported success. Contrast the Edit-panel path (`DogDialogs.tsx`), which calls `onUpdate(dog.id, convertDogToDogInput(...))` to persist. **Files:** `apps/myk9show/src/components/dogs/DogDetailsMain/index.tsx` (`handlePhotoSave` + drop/file-input handlers + photo state), `apps/myk9show/src/components/dogs/DogDetailsMain/DogDialogs.tsx` (PhotoDialog wiring + the unconditional success toast/celebration), `apps/myk9show/src/components/dogs/DogDetailsMain/utils.ts` (new `saveDogPhoto`), `apps/myk9show/src/components/dogs/DogDetailsMain/types.ts` (`onPhotoSave` signature + `isSavingPhoto`), `apps/myk9show/src/components/common/PhotoDialog.tsx` (`isSaving` prop), `apps/myk9show/src/services/imageUploadService.ts` (`uploadDogPhoto` — already existed), `apps/myk9show/src/services/mappers/dogMappers.ts` (`mapDogInputToUpdate` maps `imageUrl` → `image_url`). **Solution / RESOLVED 2026-06-03:** Extracted `saveDogPhoto({ ownerId, dogId, file, onUpdate })` in `utils.ts`: (1) upload the real `File` to Supabase Storage via the existing `uploadDogPhoto()` helper (unique timestamped path → no cache-bust needed), (2) persist the returned durable URL through the same `onUpdate(dogId, { imageUrl })` mutation the edit panel uses (`updateDog` → writes IndexedDB + background Supabase sync), (3) return a typed result so the UI never reports a false success. `index.tsx` now keeps the raw `File` (not just the data-URL preview), `handlePhotoSave` is async with an in-flight `useRef` guard + `isSavingPhoto` state, and `DogDialogs` gates the success toast/celebration on a real save. `PhotoDialog` gained an optional `isSaving` prop (Saving… label, blocks close + re-submit). Assertion-first unit tests in `__tests__/saveDogPhoto.test.ts` prove the Storage URL — not a `data:` URL — is what reaches `onUpdate`, and that failure paths don't persist or claim success. **Follow-up (separate, lower severity):** the person-details twin `UserDetailsTabs.handleUpdateDogPhoto` (`apps/myk9show/src/components/users/UserDetails/UserDetailsTabs.tsx`) persists via `updateDog({ imageUrl: <base64> })` — it survives reload but stores a base64 data URL instead of uploading to Storage; `DogCard.onSavePhoto` is currently dormant (no parent wires it).
