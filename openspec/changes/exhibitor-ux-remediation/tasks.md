## 2. Cart integrity (audit #3)

- [~] 2.1 Verify server-side behavior: does entry submission/checkout reject closed shows? — **confirmed gap**: no migration/RPC (`submit_show_entries`, checkout) checks `entries_close`/`entry_close_date` server-side. This is a money-path change (migration + `db push`) that needs explicit confirmation per CLAUDE.md Auto Mode rules — **paused, see checkpoint note below**. Client-side gate (2.2/2.3) now fails closed in the UI regardless.
- [x] 2.2 Cart load: mark/remove items whose show's entries-close has passed; exclude from payable total with explanation — `CartSummary.tsx` computes `entriesClosed` from the already-joined `cart.show.entry_close_date` and shows an explanatory banner in place of the expiration-hold warning. **Codex review (PR #1217) P1 fix:** the first cut parsed the DATE-only `entry_close_date` via `new Date(str)` (UTC midnight), which in a timezone behind UTC disabled checkout for the *entire* final entry day; now parsed by its own Y/M/D components as a local calendar date, so the boundary is the start of the day AFTER the close date. **P2 fix:** a 60s tick re-evaluates so a cart left open across midnight self-corrects instead of staying enabled until reload. Boundary cases pinned with fake timers in `CartSummary.test.tsx` (final-day-open, day-after-closed).
- [x] 2.3 Disable pay/confirm for expired items client-side — Pay button is disabled and relabeled "Entries closed — cannot pay online" when `entriesClosed`.
- [x] 2.4 Add non-empty cart affordance to the exhibitor navigation — **root cause found**: the badge (`AppHeader`'s cart icon) already existed and was wired to the cart store's `useCartItemCount()`, but nothing ever loaded the store outside of `/cart` itself — so a cart from a prior session was invisible on every other page, matching the audit's "no cart icon exists anywhere" observation. **Final approach (after two Codex review rounds on PR #1217):** the badge is now driven by a dedicated READ-ONLY count query (`useActiveCartItemCount`) that never writes the shared cart store. The first cut had the header call `loadActiveCart` (a store write); even after route-guarding it, an in-flight unscoped load started on an ordinary route could still resolve *after* the registration wizard's show-scoped `loadCart`/`createCart` and overwrite the show-specific cart, routing later `addItem` calls to the wrong cart. Reading the count directly removes the store from the header's path entirely, so the race class is gone. The store still drives the badge where it genuinely owns the cart (on `/cart` and in the registration wizard, where it's loaded and updates optimistically); everywhere else the query supplies it. Pinned by `AppHeader.cartHydration.test.tsx` (badge reflects the query; header never calls store cart-loading actions).
- [x] 2.5 Unit tests — added `CartSummary.test.tsx` (closed-show gating: disabled button + banner vs. open-show pay-enabled state) and updated the three `AppHeader` test files' `cartStore` mocks for the new `loadActiveCart`/`loadInitiated` usage. `CartSummary.source.test.ts` (pre-existing regression pins) still green.

## 4. Landing dates & venue (audit #5, #15)

> **Correction:** the audit report and this change's proposal/design named the "heritage" theme, but tracing the actual rendered markup ("Trial particulars" / "The roster" eyebrow text) showed the show walked during the audit uses the **monogram** theme (`features/monogram/landing`), not heritage. Both themes carry the identical bug (they're documented siblings — `monogram/landing/utils/dateFormat.ts` "Mirrors features/heritage/landing/utils/dateFormat.ts verbatim"), so both are fixed below; monogram is the one that reproduces the audit's exact observed symptom.

- [x] 4.1 Route date rendering through timezone-anchored helpers, but only for genuine timestamps — **root cause**: `shows.start_date`/`end_date`/`entry_close_date` are DATE-only columns ("2026-08-01", no time component). `new Date('2026-08-01')` parses as UTC midnight; formatting that instant in a timezone behind UTC (America/Chicago for a Tulsa, OK show) rolled the date back a day ("Jul 31 – Aug 2" instead of "Aug 1–3") even though the helper was already correctly timezone-aware — the bug was applying timezone conversion to a value that was never an instant in the first place. Fixed in both `monogram/landing/utils/dateFormat.ts` (`formatDateInTimezone` + `formatDateRange` — the one actually exercised) and `heritage/landing/utils/dateFormat.ts` (`formatDateInTimezone` + `formatJourneyDate`, same latent bug): a date-only string now parses via its own Y/M/D components (no UTC conversion) and formats with no `timeZone` option; a genuine timestamp still converts through the trial's IANA timezone as before.
- [x] 4.2 Venue falls back to the show address — monogram's `HeroBlock` Venue meta-cell showed "TBA" whenever the structured `venueName`/`venueCity` fields were unset (they're permanently `null` in `useMonogramLandingData.ts` — never wired to real data), even though the full street address was already available as `venueAddress` and correctly displayed elsewhere on the same page (`MonogramFooter`). Added an optional `venueAddress` prop to monogram's `HeroBlock`, wired from `MonogramLandingPage`, falling back to it only when neither `venueName` nor `venueCity` is set. Heritage has the identical `venueName: null` stub but its Hero doesn't render a "TBA" fallback (an empty `locationLabel` just hides the row) — not user-visible there, left as-is.
- [x] 4.3 Unit tests — `monogram/landing/utils/dateFormat.test.ts` (6 cases, including the audit's exact "Jul 31 – Aug 2" cross-month case), `heritage/landing/utils/dateFormat.test.ts` (5 cases), `monogram/landing/sections/HeroBlock.test.tsx` (3 cases: address fallback, structured-venue precedence, true-TBA-when-nothing-known). Full monogram + heritage suites: 246/246 passing.

## 6. Polish batch (audit #8, #9, #10, #11, #12, #13)

- [x] 6.1 Dogs delete: invalidate + toast — **root cause**: the dogs list query (`getAllDogs`) falls back to the same offline-first `replicatedDogsTable` IndexedDB store the delete flow cleans up, so the mutation's own `onSuccess` invalidate/refetch could race that cleanup and refetch a still-present local row, resurrecting the just-deleted dog until a full reload. Fixed with a second `invalidateQueries` in `useDogStoreCompat.deleteDog` after the IndexedDB cleanup settles (closes the race regardless of which order the two async ops land in — reordering them outright was considered and rejected, since deleting locally before the server mutation confirms would risk losing the dog's local record if the mutation then failed). Added a success toast in `DogDetailPage.handleDeleteDog` (`notifications.success`).
