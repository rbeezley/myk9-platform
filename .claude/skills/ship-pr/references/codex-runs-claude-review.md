# Codex-authored PRs: running the Claude review gate

Read this only when **Codex** is the author and Claude Code is the reviewer (`ship-pr` Step 4). It is the sandbox, detach/wait, supervision and replacement procedure for `scripts/qa/claude-review.sh`. A Claude-authored PR runs `pnpm qa:codex-review --post` and never needs this file.

**Codex: this cannot run inside your sandbox.** The review needs the macOS Keychain (Claude's credentials) and the network; `workspace-write` denies both, which reads as `Not logged in · Please run /login` (Keychain) or a three-minute hang ending in `Can't reach the API server` (network). The wrapper now detects both in seconds and exits 2 with the remedy: re-run it with escalated permissions, and if your approval policy forbids escalation, stop and report exactly: "Richard, run `bash scripts/qa/claude-review.sh --detach --post <pr>` from a terminal." If `--detach` or `--wait` reports that the detached review **died** or is **gone without recording a verdict**, the attempt has no verdict. A host reaping background processes when a shell call returns is one possible cause (#2131); do not infer the cause from the stale marker alone. Before a new attempt, check the PR worktree with `git merge-base --is-ancestor d04d74f93 HEAD` (#2132 introduced PID/token tracking). If it fails, do not start the branch's old wrapper: with a clean worktree, fetch and merge `origin/main`, resolve any conflicts, validate and push the resulting head before review. An existing script can still be stale; the missing-script check below is not sufficient. Before inspecting existing state, follow the replacement-coordination rules below; do not apply the new liveness probe to unknown or pre-#2132 state. Do not repeatedly poll an older wrapper's stale "running" marker. Do not substitute a same-harness subagent review; that is not the gate.

**Observed Codex workaround (#2136, 2026-09-08).** An escalated detached attempt disappeared without a verdict; its cause was not confirmed. Keeping the supervising shell open during subsequent attempts produced five completed reviews. This is a verified workaround, not proof of a root-cause fix.

For this workaround, use Codex `exec_command` with escalated permissions, the **verified PR worktree as `workdir`**, and `yield_time_ms: 1000`. Inside that command, first run `PR_NUMBER="$(gh pr view --json number --jq .number)" || exit 2`; variables from an earlier tool call do not persist. Use **two separate wrapper invocations in that one shell**. After resolving `PR_NUMBER` and confirming the original-attempt ownership/state checks below, execute this exact sequence (the failure gate belongs to `--detach`):

```bash
bash scripts/qa/claude-review.sh --detach --post "$PR_NUMBER" || exit "$?"
bash scripts/qa/claude-review.sh --wait 1500 "$PR_NUMBER"
```

The shell gates this on the first command's actual exit code; the initial tool yield may be empty while preflight is running and is neither success nor failure. Never combine `--detach` and `--wait` in one invocation: the wait branch takes precedence, skips the head check, and can return a prior head's saved exit code without starting a review. That stale result is not evidence for the current head. Do not end the shell between the two invocations. Poll the returned `session_id` with short `write_stdin` calls using `chars: ""` (empty input) only; do not send shell commands or control characters through stdin. The initial yield returns control without terminating the process. Use this only on a harness that supports a live session for at least 30 minutes without a hard command timeout; otherwise use Richard's terminal. Do not add an unbounded shell loop or an automatic restart.

**A replacement needs coordination first.** Before any new detach, identify the original attempt's PR, owning task/operator, and worktree. Use read-only inspection of that original worktree's `.logs/claude-review-<pr>.status`, `.pid`, and `.out` and the PR's head-specific review evidence to understand its state. **Do not invoke `--wait` as a diagnostic on another task's attempt or legacy/unknown state**: it can write exit 2 into the status file after a negative liveness check, including one caused by restricted process access. Older pre-#2132 attempts did not write PID metadata at all. Another worktree's missing files or an empty PID file prove nothing. Have the original owner confirm the child has ended before starting a replacement. If read-only process checks are denied or cannot establish the recorded PID/token identity, stop and ask Richard to inspect it in the original terminal. A successful `kill -0` with empty/denied `ps` output proves neither death nor reviewer identity. Never edit state files to force a terminal status. A fresh detach overwrites the attempt's files, and an old live child could write its verdict into the replacement's state.

For the supervised workaround only, at its 25-minute wait limit, first read the PR's review evidence for the exact current head: the child may already have posted or may post later. If matching evidence exists, handle that verdict; otherwise report **no verdict observed as of this check** with the PR and original log path, noting the child may still finish. Stop automated retries. Re-check head-specific PR evidence and coordinate with the original owner before considering any later replacement; elapsed time alone never authorizes one. Ending the supervising session does not prove the child survived or died; coordinate with the owner before any later attempt. Never kill another task's reviewer or substitute same-harness review evidence.
