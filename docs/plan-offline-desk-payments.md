# Offline desk payments: cash and check recorded with no connection (MYK9-1936 step 3)

> **Status:** Active

Linear: MYK9-1936, step 3. Builds on step 1 (#4446, every desk payment carries a client payment id) and step 2 (MYK9-1930, #4158, a desk late entry gets its entry form when it syncs). Design only; no code yet. App paths are under `apps/myk9show/src/`; queue files (`MutationManager.ts`, `mutation-*.ts`, `MutationUploadRunner.ts`, `types.ts`, `core/`) are under `packages/replication/src/`; migrations are under `supabase/migrations/`.

**Goal.** With no connection, the secretary records cash or a check on an entry form as normal. It shows as "waiting to send", counts in the form's balance, and is sent on its own when the connection returns. A refused payment is shown with its reason and stops counting. Close-out says when payments are still waiting. **Not included:** card payments at the table, refunds, "Payment Due", "Paid in Full: Online", and any change to what the Financial Report counts.

## 1. What exists, and why

- **The write is online and not optimistic, on purpose.** `hooks/useEnrollmentLedgerActions.ts:160-161`: "the server computes the new status and paid total, and a refused payment ... must not flash as recorded" (added by MYK9-677, `b8c0f35617`). The form's rows are patched only from the server's answer (`:37-60`, `:179-186`). A lost answer reads `LEDGER_UNCONFIRMED` (`:71-72`).
- **The ledger service is online on purpose.** `services/database/show-payments.ts:9-20` (`b8c0f35617`): the enrollment money and the close-out ledger read are PostgREST; the one offline money writer is the late-entry wizard, whose money rides on the entry row and becomes a ledger row on the server (`features/registration/submitOfflineLateEntry.ts:179-191`).
- **Offline, the form has no balance at all.** The enrollment money (total, paid, refund, card) is read online only: `services/database/entries/secretaryReadReplication.ts:185-208`, and `readRowsByIdChunks` throws when offline (`:147`). The form then reads "Amount not available" (`components/entries/management/enrollmentPayment.ts:209-226`, `EnrollmentCard.tsx:337-341`, MYK9-1968, `28e66341ee`). Today "Paid in Full" is disabled offline (`EnrollmentFullPaymentDialog.tsx:109`), while "Partial Payment" is not (`EnrollmentPartialPaymentDialog.tsx:145-150`) and ends in the "could not confirm" note. There is no `enrollments` replicated table (`services/replication/Replicated*Table.ts`).
- **Replay is already idempotent on the server.** The core returns the form's answer for an id it already recorded, and refuses an id reused for another form, method or amount (`supabase/migrations/20261114013900_myk9_1961_refunded_fee_not_owed.sql:442-459`). The desk wrapper also refuses a reused id with a changed date or check number, under the form's lock (`20261126061937_myk9_1936_payment_id_same_date_and_reference.sql:50-71`). A NULL amount means "whatever is still due" at the moment it runs (`20261114013900...:496-497`). A payment over the due is accepted as money on account; nothing refuses it.
- **The queue can carry an RPC that has no replica table.** `MutationManager.queueMutation` takes a table name, row id and an `rpc` with exact `args` (`packages/replication/src/MutationManager.ts:167-208`, `types.ts:230-245`). An `INSERT` with `rpc` calls `supabase.rpc(name, args)` (`mutation-execute.ts:104-135`). The acknowledgement touches a row only if one exists (`mutation-row-sync.ts:63`). Every queued write today goes through a `ReplicatedTable` (`core/ReplicatedTable.ts:366-415`); a table-less RPC mutation would be the first (read, not run).
- **Retry rules.** Transport loss retries without spending the budget (`mutation-retry.ts:41-61`). `42501` is permanent ("authorization"). `22023` is retryable for every RPC not listed in `RPC_PERMANENT_CODES` (`mutation-utils.ts:272-274`, `:399-472`), so a refused payment would today retry to `maxRetries` before it lands in the dead letters. A dead letter keeps `failureKind` and a message string, not the Postgres code (`mutation-retry.ts:68-80`).
- **Unsent work is already counted.** `services/replication/unsentWork.ts:229-252` counts every non-score queue row and dead letter once per row, so a queued payment would join the device's unsent count and the sign-out guard with no change. The wording "Waiting to send. It will be sent on its own." exists (`features/at-show/scoresNotSent/unsentScoreReason.ts:64`).
- **Identity offline.** A new queue row is stamped with the persisted user id when offline (`packages/replication/src/mutation-identity.ts:55-69`); an upload needs a bound session (`MutationManager.ts:132-143`) and is held after an owner change (`MutationUploadRunner.ts:309-315`). The server restates who may record (`private.can_record_show_payment`, `20260925181937_myk9_677_show_payments_ledger.sql:80-90`).
- **Close-out and the report.** Close-out reads the ledger online and shows "…" while paused offline (`features/show-workbench/ShowCloseoutSummary.tsx:49-72`). The upload-complete handler invalidates `[tableName]` (`providers/ReplicationSyncProvider.tsx:719-747`), which would not reach the hyphenated `['show-payments', showId]` key. The Financial Report already prints one warning line above its totals (`components/reports/FinancialReport.tsx:46`).

## 2. The shape proposed

**Where it lives.** In the shared queue, one row per payment: table `show_payments`, operation `INSERT`, row id = the client payment id, `rpc: { name: 'record_enrollment_payment', args }` with every argument explicit: enrollment id, `kind: 'payment'`, amount, method, received date (the dialog's, already explicit), check number, client payment id, and the new `p_refuse_over_due: true`. `data` holds the show id and the same figures for display only (it is not sent when `args` is present). No replica row; no `dependsOn`, so one refused payment never blocks the next.

**When it queues.** Only cash or check payments ("Paid in Full" and "Partial Payment"), and only when the device is offline at save time (`navigator.onLine === false`). Online stays the direct call it is now, so refusals still reach the open dialog with what was typed. "Paid in Full" queued offline sends the amount she was shown, never NULL, so a later "whatever is due" cannot turn into $0 or a different figure. Refunds, "Payment Due" and "Paid in Full: Online" stay online and say "Needs a connection." Recommended follow-up (PR 5): an online save whose answer never comes (a transport error) is handed to the queue under the same id, with a bounded wait; the id makes that safe.

**Replay.** The existing runner sends it when the connection returns. A send that lands but loses its answer is sent again with the same id and gets the form's answer back (core `:442-459`); nothing is written twice. Add `record_enrollment_payment → {22023}` to `RPC_PERMANENT_CODES`, so a refusal is shown at once instead of after the retry budget, and keep the Postgres code on the dead letter so the reason is matched on code plus text, the way `ledgerFailure` does (`useEnrollmentLedgerActions.ts:117-141`, extracted to a shared pure module).

**The server guard (migration).** A queued payment was priced from a copy of the form that may be stale. With `p_refuse_over_due` set, refuse (22023) a payment larger than what the form owes now: `payment % is more than the % this form now owes`. The check runs in the core after the id dedupe (`:442-459`) and after the due is computed (`:489-497`), so a replay of a payment that already landed is answered, never refused because its own money closed the form. Default `false`: online callers and `submit_show_entries` are unchanged. A changed signature means `DROP FUNCTION` of the old ones and restated grants (`20261126061937...:83-86`). This covers "another device already recorded it", "the form was refunded or comped meanwhile" (a refunded fee is not owed, MYK9-1961), and over-balance. There is no cancelled state on an entry form; a deleted one is `enrollment % not found`.

**The balance offline (needs PR 1).** The form's money must be on the device. Recommended: a read-only, show-scoped replicated `enrollments` table with the columns the online read takes (`secretaryReadReplication.ts:197-199`), and no local writes to it ever. The queued payments are an overlay, never written into that row, so the server's figures stay the server's (the "not optimistic" reason holds). The Payment line reads `$50.00 · $25.00 received · $25.00 waiting to send · $0.00 due`; the status badge stays what the server says, with a "Waiting to send" chip beside it. After a successful send, the payment shows "Sent" until the next enrollments pull for that show, so the due never jumps back up in between. Rejected alternative: keeping the last online read in a private IndexedDB key; it is a second offline store beside replication.

**A refused payment (open question 1).** Recommendation: it stays on the form's Payment section as its own line, in the warning colour, out of every total:
"Cash $25.00 (Nov 26) could not be sent. Another payment was recorded on this form while this one waited. If you took this money, record it again from Change payment."
One button, "Remove", which deletes the dead letter (`MutationManager.discardFailedMutation`, `:410`). "Try again" appears only for a `max-retries` dead letter (`retryFailedMutation`, `:398`), since a refusal would only be refused again. Reasons, by refusal: over the due (above); `42501` "You do not have permission to record payments for this show."; a received date after the show's today, the existing friendly text; anything else, "Something went wrong with this payment. Record it again from Change payment." She learns of it where she works: the device's unsent count already includes it (`unsentWork.ts`), and Show Desk's existing "Resolve N payments" pill (`features/show-map/showDeskPendingSignals.ts:196-206`) counts forms with a refused payment. No new page.

**Close-out and the Financial Report (open question 2).** Recommendation: neither changes what it counts; both say what this device has not sent. Close-out, under "Payments received", read from the device's queue, so it shows offline too: "2 payments ($50.00) on this device are waiting to send and are not in this total." and "1 payment could not be sent. Open the entry form to see why." While either line shows, the close-out chip is not "Ready". The Financial Report prints one line beside its existing warning: "2 payments recorded on this device ($50.00) are waiting to send and are not counted below." Both say "on this device": another device's queue is not visible here, and the copy must not imply it is. On upload, invalidate `['show-payments']` explicitly.

**A form only on the device** (late entry not synced, no enrollment id). Refuse until synced: keep `SAVED_ON_DEVICE_PAYMENT_NOTE` (`enrollmentPayment.ts:201-202`). The money taken when the entry was made is already offline (the wizard's entry columns); a second payment on an unsynced form is rare, and queuing it would need a new RPC keyed by entry id.

**Identity and permission.** Queue only when the queue owner resolves (the persisted user id); if it does not, show the "write it down" note below rather than queue under no one. The menu is shown where it is today; the server decides at replay, and a `42501` is a refusal shown as above. A different account signing in holds the row (`MutationUploadRunner.ts:309-315`); the sign-out guard already counts it.

**Migration.** One, for `p_refuse_over_due` (PR 2). PR 1 may need none: check that every writer of enrollment money moves `updated_at` (the core does, `20261114013900...:532`; the card-money writers are not checked) and that `enrollments_select` admits the secretary for a show-scoped pull.

## 3. Do nothing, delete it, or link to what exists

Keep it online only, and make both dialogs say plainly when offline: "No connection. Write the payment down and record it here when you're back online." Cost: one small PR, no risk, and it fixes today's mixed state (one dialog disabled, one that ends in "could not confirm"). Against it: the owner already rejected "only tell her she is offline"; it puts a paper side ledger back on show day, where `docs/goals/fall-2026-launch-readiness.md:71` asks for "offline-tolerant, and hard to mess up"; and close-out would not know about the paper. Verdict: not the answer, but the note is right for the cases that stay online (refunds, "Payment Due", an unsynced form, an unresolved identity), and PR 3 ships it for them.

## 4. Sizing and split

Five PRs, one concern each. Money work and migrations do not batch.

1. **Form money on the device.** Read-only `enrollments` replica, show-scoped, used by the secretary read when the online read is unavailable. Done when: a cold offline reload of Entry Management shows each synced form's total, received and due; "Amount not available" only for a form never synced; nothing writes to the replica locally.
2. **Server guard.** Migration adding `p_refuse_over_due` (default false), grants restated, SQL behavioral test, and the new refusal in the friendly list. Done when: an over-due flagged payment is refused with the exact text; an unflagged one behaves as today; a replay of a landed id is answered, not refused. `supabase db push` before PR 3 merges.
3. **Queue, replay and refusal on the form.** Queue builder, `RPC_PERMANENT_CODES` entry and code on the dead letter (`packages/replication`, rebuild dist), the overlay on the Payment line, the refused line with "Remove", and the "needs a connection" note for what stays online. Done when: acceptance criteria 1, 2, 3 and 5 hold.
4. **Close-out and Financial Report lines.** Done when: criterion 4 holds offline and online, the chip is not "Ready" while a payment waits, and the report counts what it counted before.
5. **Optional: lost answer goes to the queue.** An online save with no answer after a bounded wait is queued under the same id and reads "Waiting to send" instead of "could not confirm".

## 5. Testing

- **Unit.** Assertion-first on the queue call: `expect(queueMutation).toHaveBeenCalledWith('show_payments', 'INSERT', id, …, { name: 'record_enrollment_payment', args: expect.objectContaining({ p_client_payment_id: id, p_amount: 25, p_refuse_over_due: true }) })`. Retry classification: `22023` on this RPC is permanent, on other RPCs unchanged; transport keeps retrying. Overlay math: waiting counts in due, refused does not, sent holds until the pull. Refusal mapping by code and text. `summarizeUnsentWork` counts a payment as one other change. Close-out and report lines, with geometry-free behavior assertions (rendered text, chip state).
- **SQL behavioral** (`supabase/tests/`, runs in CI only): the guard refuses over-due; a landed id replayed after the form is fully paid is answered, not refused; unflagged callers unchanged; grants checked against the applied database after the push.
- **Replay twice.** A MutationManager test whose first send commits and then throws a transport error, and whose second gets the answer: one ledger row, the queue empty, no dead letter. The SQL test proves the server half.
- **Offline e2e** (one spec, a row in `docs/qa/e2e-suite-map.md`). Using a seeded form with money due (check `supabase/seed-demo.sql` first): go offline in the browser, record cash, see "Waiting to send" and the reduced due, see the close-out line; go back online, see it clear and one ledger row. Refused case: staged in the browser by answering the RPC with a 22023 body through route interception, never by writing to the shared database.
