## Why

myK9Show already has canonical modules for both dates and statuses — `apps/myk9show/src/lib/format/dates.ts` is explicitly self-documented as "the single app-facing module... do not invent new ones at call sites," and `apps/myk9show/src/services/entryDisplay/entryDisplaySelectors.ts` was built specifically to stop three surfaces (exhibitor My Entries, Show Details "My Entries" tab, secretary Entry Management) from disagreeing on entry status. Both are routinely bypassed. At least 9 other `formatDate`-named functions exist across `packages/core/src/utils/dateFormatting.ts`, `apps/myk9show/src/utils/{dateFormat,dateLocal,date-format,entryManagementUtils}.ts`, two secretary page-local `utils.ts` files, and `components/sync/conflict-resolution-utils.ts` — producing visibly different output for the same kind of date (e.g. `"Jul 3, 2026"` vs `"7/3/2026"` vs `"7/3/2026, 2:00:00 PM"` vs the canonical module's `"Fri, Jul 3, 2026"`). Status badges show the same split: `components/exhibitor/EntryRow.tsx` and `utils/entryStatusUtils.ts` each define their own status-to-label/color map independent of the shared classifier, and `components/classes/ClassResultsTable/StatusBadge.tsx` derives a "Scored/Editing/Pending" badge from local booleans with no shared config at all. Separately, `features/monogram/landing/sections/{FinalCtaBand,HeroBlock}.tsx` render a "Closes {date}" label keyed only on `entryCloseDate` being present, not on whether the show's registration is actually still open (`canEnterOnline`) — so the label can keep telling a visitor entries are closing on a date that has already passed. This is exactly the fragmentation the current consolidation phase exists to close: the same fact should look and read the same everywhere it's shown, using the canonical modules that already exist rather than growing new ones. Note: `entryDisplaySelectors.ts` documents that some copy differences (e.g. "Pending Review" for exhibitors vs "Pending" for secretaries) are intentional, not bugs — this proposal targets undocumented drift, not that documented choice.

## What Changes

- Migrate call sites off the ~9 duplicate `formatDate`-style functions onto the existing canonical `apps/myk9show/src/lib/format/dates.ts`, keeping only the timezone-aware per-landing-page `formatDateInTimezone`/`formatDateRange` copies (they render public marketing pages in the show's own timezone, a documented, distinct need) and removing the rest.
- **[CORRECTED after per-function review]** Reading each "duplicate" function's actual implementation showed the original ~9 count conflated real duplicates with distinct utilities that happen to share the name `formatDate`. The genuine short-date display duplicates (all render `"Jul 3, 2026"`) are `entryManagementUtils.ts formatDate` (1 call site), `WaitlistManagementPage/utils.ts formatDate` (1 call site), and `lib/utils.ts formatDate` (1 call site) — these three consolidate onto one new short-date helper in `lib/format/dates.ts`. `dateLocal.ts formatDateDisplay` duplicates the numeric `formatDateMMDDYYYY` family (already deduped above), not this family. Three functions are **not duplicates and are excluded from this change**: `conflict-resolution-utils.ts formatDate` is a relative-time formatter (`date-fns`'s `formatDistanceToNow`, "2 hours ago"), unrelated to date display; `dateLocal.ts formatDateLocal` converts a `Date` **to** a `YYYY-MM-DD` string for form/storage use, the inverse of a display formatter. `WaitlistManagementPage/utils.ts formatDateTime` and `ResultsSubmissionPage/helpers.ts formatDate` both independently invented a date+time display (a real but different fragmentation from the one originally described, since the canonical module has no date+time helper) — these two get a new canonical `formatEntryDateTime` in `lib/format/dates.ts` and migrate onto it.
- **[ADDED after scope review]** Deduplicate `formatDateMMDDYYYY`, which is defined identically in both `packages/core/src/utils/dateFormatting.ts` and `apps/myk9show/src/utils/dateFormat.ts` and has 16 call sites across dog Pedigree/Competitions/TitleTracking/Registrations, `TrialDetail`, and `RegistrationWorkflow` — none of which were in the original affected-code list. This is a compact numeric date style (`"8/1/2026"`) distinct from the canonical module's prose weekday style, and per this change's Non-Goal against redesigning visual output, it is **deduplicated in place** (the app-local file re-exports from `@myk9/core` instead of redefining), not migrated onto `lib/format/dates.ts`. All 16 call sites already import from the app-local `@/utils/dateFormat` wrapper, so none require changes — this is a single-file fix.
- **[CORRECTED — no code change, see design.md]** All three "independent status-to-label/color maps" turned out on inspection to need no migration: `components/exhibitor/EntryRow.tsx`'s map is dead code (zero importers); `utils/entryStatusUtils.ts` classifies a show's registration-window state, a genuinely different domain from `entryDisplaySelectors.ts`'s per-entry lifecycle classifier, not a duplicate of it; `components/classes/ClassResultsTable/StatusBadge.tsx` stands alone but migrating it onto `packages/ui/src/components/StatusBadge` would visibly change its appearance, which this change's Non-Goals rule out — left as-is by design decision.
- **[EXPANDED — confirmed systemic]** Fixed the "Closes {date}" gating bug not just in `features/monogram/landing/sections/{FinalCtaBand,HeroBlock}.tsx` but in the identical pattern found in 5 of the other 6 sibling landing themes (`gazette`, `magazine`, `fieldGuide`, `banner`, `poster` ×2) plus 2 more instances in `headline` theme — 8 files total, all fixed using the already-existing shared `useCountdown(entryCloseDate, timezone).closed` signal (not `canEnterOnline`, which the proposal originally named incorrectly — see design.md). `heritage/HeroBlock.tsx` already did this correctly and served as the reference pattern. Each theme's `ParticularsSection.tsx` detail-table rows were deliberately left untouched — those show entry-window dates as historical reference facts, not an active "still open" claim, so hiding them post-close would make the reference table incomplete.
- **BREAKING** (internal only, no external API): remove the redundant per-file `formatDate` exports; any code importing them directly must switch to the canonical import path.

## Capabilities

### New Capabilities
- `date-formatting`: The rule that all app-facing date display goes through `lib/format/dates.ts`, the catalogue of allowed formats, and the documented exception for timezone-bound public landing pages.
- `status-display`: The rule that entry/class/check-in status labels, colors, and icons resolve through the existing shared classifiers rather than page-local maps, including the requirement that any date-derived status label (e.g. "Closes {date}") reflect the record's *current* status, not just the presence of a date field.

### Modified Capabilities
- None — no existing `openspec/specs/` capabilities exist yet in this store; this proposal defines the first two.
