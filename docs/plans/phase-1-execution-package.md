## 1. Phase 1b — The single email-or-passcode field

### 1.1 Visual + structure

One field, one submit button, two helper regions (static discoverability + live disambiguation). The field is a controlled `useState` input — same pattern as the current `email` state in `SignInPage.tsx`.

```
┌─────────────────────────────────────────────┐
│  myK9Show                                     │
│                                               │
│  Sign in or join a show                       │  ← H1
│                                               │
│  ┌─────────────────────────────────────────┐ │
│  │ 📧  Email or show passcode               │ │  ← single field
│  └─────────────────────────────────────────┘ │
│  › Looks like an email — we'll ask for your   │  ← aria-live disambiguation
│    password next                              │
│                                               │
│  [ Continue ]                                 │  ← disabled until valid shape
│                                               │
│  Have an account? Use your email.             │  ← static discoverability
│  Working a show? Use the passcode your         │
│  secretary gave you (5 characters).            │
│                                               │
│  Learn how it works →  (/help/credentials)    │
└─────────────────────────────────────────────┘
```

### 1.2 Client-side disambiguation logic (pure, testable)

A pure function `classifyCredential(raw: string): 'email' | 'passcode' | 'invalid'`. Extract to a sibling helper module (e.g. `SmartInput.helpers.ts`) so it is unit-testable without rendering — same split precedent as `SignInPage.helpers.ts`.

**Normalization (runs before classification, on every keystroke for display and again on submit):**
1. Trim leading/trailing whitespace **and** zero-width chars (`\u200B`, `\uFEFF`).
2. Lowercase the entire input.
3. Reject internal whitespace/newlines → `invalid`.

**Classification order (first match wins):**
1. Contains `@` → `email`. (Do not validate the full RFC email here; defer real validation to Supabase. `@`-presence is the branch signal only.)
2. Matches passcode shape → `passcode`. Reuse `parsePasscode()`: `length === 5` AND `isValid === true` (first char ∈ `a|j|s|e`, remaining 4 chars `[a-z0-9]`).
3. Otherwise → `invalid`.

> **INTENT note for the implementer:** `parsePasscode` returns `{ role:'exhibitor', isValid:false }` for bad input — discriminate on `isValid`, never on the defaulted `role`. (Carryover of the `assertion-first / ui-id-shapes` memory: test `classifyCredential` with the exact strings the field emits, including a trailing-space `"eh2p9 "` and a zero-width-prefixed paste.)

### 1.3 Exact copy & ARIA (from the plan — do not paraphrase)

**Live disambiguation** (under the input, `aria-live="polite"`, single region whose text swaps):
- email branch: `Looks like an email — we'll ask for your password next`
- passcode branch: `Looks like a show passcode — you'll be signed in`
- invalid branch while typing: region is **empty** (do not nag mid-type; only the submit-time error speaks).

**Static discoverability** (always visible, before first keystroke):
> Have an account? Use your email.
> Working a show? Use the passcode your secretary gave you (5 characters).

**Error (unrecognized input on submit):**
> That doesn't look like an email or a show passcode. Passcodes are 5 characters and start with a letter — for example, `aa260`.

**"Learn how it works" link** → `/help/credentials`. Broken link is a **ship blocker** (Phase 1f). 1b must land with at least a stub page or the link gated.

### 1.4 Field attributes & keyboard

| Concern | Spec |
|---|---|
| Label | Visible label `Email or show passcode` (not placeholder-only — INTENT accessibility: our users are not 25-year-old engineers). |
| `inputmode` | Default `email`; re-evaluate on each keystroke. Once classification flips to `passcode`, the field stays text-friendly so the 5-char code isn't fought by an email keyboard. |
| `autocomplete` | Step-1 field: `autocomplete="username"`. Step-2 password (email branch): `autocomplete="current-password"`. (Manual 1Password/Bitwarden/iOS Keychain/Chrome verification is a Phase-1 task.) |
| `autocapitalize` | `off` (passcodes are lowercase; emails are lowercase). |
| Submit gating | Button `disabled` + `aria-disabled="true"` until classification ∈ {email, passcode}. Enter on `invalid` fires the standard error, **not** a request. |
| Invalid submit focus | Keep focus on the input; set `aria-invalid="true"` and `aria-describedby` → the error element id. |

### 1.5 Submit behavior

- `email` → reveal step 2 (password). Do **not** navigate; transition in place (see 1.6).
- `passcode` → call the `validate-passcode` edge function immediately (no second step for anonymous users). On 200 → attach session + route (Phase 1d). On 401 → generic error. On 429 → rate-limit copy + Turnstile after 3 consecutive fails (the captcha is a Phase-1 security item; confirm Turnstile is already wired before assuming).
- **No "Forgot password?" on step 1.** It appears only on step 2 (it already lives at the bottom of `SignInPage.tsx` — keep it there).

### 1.6 Step transition (email branch → password)

The current `SignInPage` shows email + password together. The smart input reveals password **after** the email is committed. Two viable patterns:

- **Recommended:** keep the email value locked-but-visible (read-only chip with an "edit" affordance) and animate in the password field below it. Programmatic focus to password on reveal (INTENT: respect the clock, no hunting).
- The password step reuses the exact markup/handlers from `SignInPage.tsx` lines 104–175 (show/hide toggle, loading spinner, error region, forgot-password link). **DRY: factor the password sub-form out of `SignInPage` so both the smart input and `/sign-in` consume it.**

## 2. Phase 1c — Account + passcode merge + confirmation step

This is the **highest-risk surface in the whole spec** (see §5). It covers Locked Decision #8: a passcode entered by a **signed-in** account *expands role, scoped to one show* — it never impersonates.

### 2.1 Two entry conditions

| Caller state | Passcode entered where | Behavior |
|---|---|---|
| Anonymous | Smart input on landing | Validate → passcode session → route by role (1d). No confirmation step. |
| **Signed-in account** | Smart input (or a "join with passcode" affordance inside the app) | Validate → **confirmation step** → on confirm, attach passcode role *in addition to* the account session, scoped to that `show_id`. |

Detecting "signed-in" = `useAuthContext().user != null` (`AuthContextType.user`, `AuthContext.tsx:66`).

### 2.2 The confirmation step (exact copy from Locked Decision #8)

After `validate-passcode` returns `{ show_id, role }` for a signed-in user, show a confirmation before attaching. The returned `show_id` must be resolved to a show **name** for the copy (the edge function already does a `shows` lookup at line ~212; surface `show_name` in its response, or do a follow-up read).

> **You're signed in as [name]. Use this passcode to join [show] as a [role]?**

- `[name]` ← `userWithRoles.firstName` / display name from `AuthContext` (`firstName` field exists at `AuthContextType.firstName`, line 129).
- `[show]` ← resolved show name.
- `[role]` ← humanized ringside role (`admin`→"show admin", `judge`→"judge", `steward`→"gate steward", `exhibitor`→"exhibitor"). **Do not show the raw enum.** (INTENT: no software jargon.)
- Buttons: primary **Join show** / secondary **Cancel** (returns to prior context, account session untouched).

### 2.3 What "attach in addition to" means concretely

The account session stays the source of truth for identity, audit trails, and (future) push-subscription ownership. The passcode grants a *transient, show-scoped ringside role*.

**Design model (no schema work in 1c):** introduce a client-side "active ringside grant" — `{ showId, role, source: 'passcode' | 'account' }` — held in auth context state (Zustand or an `AuthContext` extension; **decision flagged §5-D**). The `RingsideProvider` value at `/at-show` is then built from this grant, **not** from `toRingsideRole(accountRole)` directly:

```
ringsideRole =
  activeGrant?.role                       // passcode-attached, show-scoped
  ?? toRingsideRole(accountRole)          // 1a fallback for passcode-less account users
```

This preserves the 1a adapter's INTENT comment (a secretary who never types a passcode still maps via RBAC) while letting a passcode *override upward* for one show. `buildRingsideAuth` (already written) takes `showRole` + `showContext` — extend its caller to pass the grant's role when present.

**Precedence rule (must be explicit in code + tested):** passcode grant wins over account RBAC role **only for the matching `show_id`**. A passcode for show X must never elevate the account's view of show Y. The grant carries `showId`; the `/at-show/:showId` route compares route param to grant `showId` before honoring it.

### 2.4 Session lifecycle

- Anonymous passcode session: lives until tab close / explicit "leave show." No Supabase session created.
- Account + passcode grant: the grant is ephemeral (clears on sign-out, on "leave show," and is not persisted across full reloads unless re-validated). **Decision flagged §5-E:** persistence of the grant across reload.

**5-D. **5-E. If yes, we must re-validate the passcode on reload (can't trust persisted grant) which means storing the *passcode* client-side (security smell) or a server-side session. **Recommendation for the spike:** grant does **not** persist; on reload, re-derive from account RBAC (`toRingsideRole`) and show a subtle "re-enter passcode to resume [role] tools" affordance. **5-H. (LOW) Enumeration-resistant generic error vs. calm UX tension.** Security wants "That credential wasn't recognized" for *all* failures (bad email, wrong password, bad passcode). );

--    No anon access: feature overrides are never read by unauthenticated clients.

GRANT ALL ON public.feature_flag_overrides TO service_role;
-- (No GRANT to anon — anonymous clients have no access.)

-- ---------------------------------------------------------------------------
-- 4. Row-Level Security
--    - SELECT: a user reads only their own row; admins read all.
--    - INSERT / UPDATE / DELETE: admins only.
--    - anon: no policy → no access.
-- ---------------------------------------------------------------------------
ALTER TABLE public.feature_flag_overrides ENABLE ROW LEVEL SECURITY;

-- SELECT: own row or admin
CREATE POLICY "feature_flag_overrides_select_own_or_admin"
  ON public.feature_flag_overrides
  FOR SELECT
  TO authenticated
  USING (
    public.is_site_admin()
    OR person_id IN (
      SELECT id FROM public.people WHERE auth_user_id = auth.uid()
    )
  );

-- INSERT: admins only
CREATE POLICY "feature_flag_overrides_insert_admin"
  ON public.feature_flag_overrides
  FOR INSERT
  TO authenticated
  WITH CHECK (public.is_site_admin());

-- UPDATE: admins only
CREATE POLICY "feature_flag_overrides_update_admin"
  ON public.feature_flag_overrides
  FOR UPDATE
  TO authenticated
  USING (public.is_site_admin())
  WITH CHECK (public.is_site_admin());

-- DELETE: admins only
CREATE POLICY "feature_flag_overrides_delete_admin"
  ON public.feature_flag_overrides
  FOR DELETE
  TO authenticated
  USING (public.is_site_admin());

 * Phase 1a placeholder. Host normally writes the chosen area count +

          {n} {n === 1 ? 'area' : 'areas'}
        </button>

    </div>
  );
