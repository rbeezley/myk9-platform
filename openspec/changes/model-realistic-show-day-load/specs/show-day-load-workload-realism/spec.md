## ADDED Requirements

### Requirement: Scoring concurrency never exceeds one session per class

The load scenario SHALL assign at most one `ringside-scoring` session to any class at any time, and the total scoring session count SHALL equal the sum of concurrent rings across the shows in the fixture.

Seven concurrent scorers per class is the condition that produced a 9.4 s scoring-write p95 in run 33075234998, by serializing on the row-exclusive lock `refresh_class_scoring_state` takes on the class row. A class is scored by one judge, one dog at a time. Any scenario that violates this measures queueing rather than platform behavior.

#### Scenario: Scoring sessions map to distinct classes

- **WHEN** session assignments are built for any scenario
- **THEN** no two `ringside-scoring` sessions resolve to the same class ID, and the scoring session count equals the fixture's total ring count

#### Scenario: A scenario over-subscribes a class

- **WHEN** a scenario declares more scoring sessions than the fixture has rings
- **THEN** scenario construction fails with an error naming the over-subscribed class, rather than silently distributing by modulo

### Requirement: The fixture spans concurrent shows

The load fixture SHALL contain multiple shows with distinct classes and entries — one large show of eight rings and three mid-size shows of four rings each — and every session SHALL be assigned to a show as well as to a class.

Concurrent shows are how the platform is actually used, and they are the only way to observe cross-show replication volume. `dogs` and `classes` both skip their scope filter when no scope value is supplied, so a staff session's sync pulls deltas generated by every other running show. A single-show fixture cannot surface that at any session count.

Carrying a show ID does not make a session show-scoped. `entries_select` admits
`show_id IN (SELECT manageable_show_ids())`, so a staff credential that can manage all four
fixture shows sees all four regardless of which show its session targets. The current
runner clones one secretary auth state across every secretary session, which would collapse
the own-show versus cross-show distinction this fixture exists to measure. Each staff
session SHALL therefore authenticate as an identity that can manage only its assigned show.

#### Scenario: Sessions are show-scoped

- **WHEN** the fixture is built
- **THEN** each session carries a show ID, and classes and entries belonging to one show never appear in another

#### Scenario: Staff credentials are scoped to one show

- **WHEN** a staff session authenticates
- **THEN** `manageable_show_ids()` for that credential resolves to exactly its assigned show, asserted before the load begins rather than assumed from the fixture

#### Scenario: Cross-show delta volume is observable

- **WHEN** a rehearsal runs with concurrent shows generating writes
- **THEN** the evidence reports `classes` replication delta volume attributable to shows other than the session's own, and reports scoped versus unscoped sync counts and per-poll cost for both `classes` and `dogs`

### Requirement: The workload mix reflects observed show operations

The scenario SHALL be read-dominant, with writer sessions bounded by ring count and reader sessions scaled from exhibitor count, and every session count SHALL be a documented parameter carrying its provenance.

The prior workload was frozen at 55 scoring sessions and preserved verbatim across three changes without ever being modelled. Recording provenance is what prevents a number from becoming an invariant by inertia.

#### Scenario: Counts declare their origin

- **WHEN** a scenario parameter is read
- **THEN** it is accompanied by whether it is operator-observed or estimated, and estimates identify what would replace them

The check-in workload SHALL exercise the **exhibitor self-check-in** path: exhibitor
credentials, entries the authenticating person owns or handles, and the self-check-in
mutation. Constraining only the arrival pattern would allow the existing
`secretary-check-in` workload and its staff auth state to satisfy this requirement while
exercising different authorization and a different mutation path, then be reported as
exhibitor-driven coverage.

#### Scenario: Check-in bursts at class start

- **WHEN** the check-in workload runs
- **THEN** its arrival pattern is bursty at class start rather than uniform, so it contends with the judge on that class in the way real check-in does

#### Scenario: Check-in uses the exhibitor path

- **WHEN** a check-in session performs its write
- **THEN** it is authenticated as an exhibitor acting on an owned or handled entry through the self-check-in path, not as staff through the secretary mutation

### Requirement: Generation fits the runner budget without misrepresenting coverage

Writer sessions and a per-runner reader sample SHALL be generated by real browsers. Remaining reader load MAY be generated as API-level virtual users, provided each reproduces the delta-sync cadence, watermark advancement and endpoint mix of a real reader session.

Evidence SHALL state how many sessions of each class were browser-generated versus API-generated.

An API-level reader issues the same requests but never paints, so it cannot catch a client-side rendering regression. A passing run must not be readable as browser-verified coverage it does not have.

#### Scenario: Evidence distinguishes generation modes

- **WHEN** aggregate evidence is written
- **THEN** it reports browser-generated and API-generated session counts separately, per workload kind

#### Scenario: Virtual users diverge from real request patterns

- **WHEN** an API virtual user's endpoint mix or sync cadence does not match the replication layer's own
- **THEN** the contract test fails rather than allowing a fiction to be measured

### Requirement: Shape-dependent targets are re-derived before they gate

Gate eligibility SHALL be decided per target, not per scenario. A target whose value
depends on workload shape SHALL be informational until derived from a valid rehearsal
against the reshaped workload. A target that asserts a shape-independent invariant SHALL
continue to gate throughout.

`apiP95Ms: 200` and `scoringWriteP95Ms: 200` were set against a workload that cannot occur,
and `throughputMin: 50` was calibrated to 100 sessions; all three move with how many
sessions do what. Carrying them forward would be meaningless and inventing replacements
ahead of measurement would repeat the error this change corrects. But a lost scoring write,
a replication queue that never drains, an unreconciled persistence count or an invalid
attribution is a defect at any workload, and suspending those would open the gate far wider
than the remodel requires.

Initial split:

| Informational until derived | Gating throughout                               |
| --------------------------- | ----------------------------------------------- |
| API p95                     | Session-lifecycle consistency                   |
| Scoring-write p95           | Replication queues drain to zero                |
| Throughput                  | Replication queue telemetry complete            |
|                             | Persisted scores reconcile                      |
|                             | Platform telemetry present and complete         |
|                             | Peak connections within the verified cap        |
|                             | Generator attribution valid, no saturated shard |
|                             | Error rate and availability                     |

Error rate and availability sit in the gating column because a request either succeeded or
it did not, and the threshold is a product decision rather than a workload artifact. They
are the likeliest to need revisiting: sustained latency produces client timeouts, which
depress availability without any request being served incorrectly. If the first valid
reshaped run shows either systematically driven by shape, moving it to the informational
column is permitted **only** with a recorded reason.

#### Scenario: A shape-dependent target is exceeded before derivation

- **WHEN** API p95, scoring-write p95 or throughput misses its placeholder value before targets are derived
- **THEN** the run reports the measurement, does not fail the gate, and states that the target is pending derivation

#### Scenario: A shape-independent invariant fails

- **WHEN** queues do not drain, persistence does not reconcile, telemetry is incomplete, connections exceed the verified cap, or attribution is invalid
- **THEN** the run fails the gate regardless of whether shape-dependent targets have been derived

#### Scenario: Targets are derived from observation

- **WHEN** a shape-dependent target is set
- **THEN** it cites the valid run it was derived from and the margin applied, and moves to the gating column

#### Scenario: A target changes column

- **WHEN** a target moves between informational and gating
- **THEN** the move records why, so the gate's coverage cannot narrow silently
